# Run — evaluation-gate mechanism: demo decisions and the threshold sweep

## Commands

```bash
cd platform/safety-governance/01-eval-gates/core
python3 eval_gate.py demo                        # candidate-0000, seed 0, n=200
python3 eval_gate.py demo --candidate-index 42   # candidate-0042, seed 0, n=200
python3 eval_gate.py sweep                       # n=2000, seed 0, category ceiling disabled (1.10)
```

## Hardware and cost

CPU only (no GPU involved — pure Python, no dependencies beyond the standard
library), all three commands complete in well under a second combined.
Cost $0. Every candidate's score is synthetic, generated by this script's own
`generate_synthetic_candidates` with a fixed seed — there is no real model or
real eval suite behind any number below.

Both rules fire independently here (every category over the 0.70 ceiling,

every reason that fired, not just the first one found.

## Result 4: what the two-rule combination hides

The README's demo values (category ceiling 0.70, aggregate delta 0.15) sit
at delta_ceiling=0.15 on this same candidate population, where this isolated
sweep already shows false_block_rate=0.275 and false_pass_rate=0.000 from
the aggregate rule alone. Running the *original* two-rule sweep (category
ceiling varied from 0.40 to 1.15 in steps of 0.05, aggregate delta fixed at
0.15) over the same 2000 candidates gives:

```
    1.10             0.275             0.000

```

Past ceiling 0.65 the category rule stops changing the outcome at all —
false_block_rate plateaus at exactly 0.275, matching Result 3's number for
delta_ceiling=0.15. The aggregate-delta rule is doing all the work past that
point; sweeping the category ceiling alone would make it look like the gate
had reached some inherent floor, when the floor is actually set by the
*other* rule. A gate combining several rules cannot be tuned by varying one
threshold at a time and reading the result as if the others were absent.

## What this does not establish

- **Nothing about real model safety evaluation.** Every score is a synthetic
  number generated by `generate_synthetic_candidates`; no real capability,
  eval suite, or model output was measured.
- **Nothing about where a real gate's crossover threshold should sit.** The
  0.35-0.40 crossover in Result 3 is a direct artifact of this script's own
  synthetic-data construction (baseline 0.35, true-unsafe cutoff 0.70), not
  a recommendation for any real policy's threshold.
- **Nothing about which categories or how many a real framework should use.**
  The four category names are illustrative labels borrowed from public
  framework category types, not a claim that this is a complete or correct
  taxonomy.
