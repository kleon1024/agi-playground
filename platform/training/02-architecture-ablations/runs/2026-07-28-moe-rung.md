# The MoE rung — dense against mixture-of-experts under two budget definitions

The first rung of this ladder to run on real tokens rather than as a CPU smoke
test. Three arms, three seeds each, 200M tokens per run, nine runs in total.

## Command

```bash
cd platform/training/02-architecture-ablations/core
python ablate.py --rung moe \
    --data ~/agi-playground/data/tokens \
    --seeds 3 --tokens 2e8 \
    --budget "both: equal-active and equal-total arms, declared per arm" \
    --out ~/moe-ablation.json
```

## Model and hardware

The control is a small sibling of the mission's 88M configuration, not the
configuration itself: 8 layers, `d_model` 512, 8 query heads over 8 KV heads,
`d_ff` 1368, 512-token sequences, the same 16,512-token vocabulary, RMSNorm,
RoPE, SwiGLU. Data is the same FineWeb-Edu token files stage 02 pretrained on,
memory-mapped and read with a per-seed batch sequence that is identical across
arms.

| | |
|---|---|
| GPU | NVIDIA GeForce RTX 4090, 24,564 MiB, driver 591.86 |
| Host | WSL2 on Ubuntu 22.04.3, reached over Tailscale |
| torch | 2.13.0+cu130, bf16 autocast, fused AdamW |
| Schedule | 3e-4 peak, 2% warmup, cosine to 0.1x, identical for every arm |
| Total GPU time | 3.42 hours across all nine runs |
| Cost | $0 (local lane) |

## The three arms

A mixture-of-experts block has two parameter counts, so "equal budget" has two
readings and `moe_arms()` returns both rather than picking one. Every arm uses
8 routed experts with top-2 routing plus 1 shared expert; only the per-expert
width changes.

| Arm | `expert_d_ff` | Total parameters | Active per token |
|---|---:|---:|---:|
| `dense` | — | 33,661,440 | 33,652,736 |
| `moe-equal-active` | 456 | 67,314,176 | 33,685,504 |
| `moe-equal-total` | 152 | 33,694,208 | 22,478,848 |

`456 = 1368 / (2 active + 1 shared)`, rounded to a multiple of 8, which lands
active parameters within 0.10% of dense. `152 = 1368 / (8 routed + 1 shared)`,
which lands total parameters within 0.10% of dense and leaves a token passing
through 66.8% of them.

## Result

Validation loss on the same held-out batches (`seed=999`) for every arm and
every seed:

| Arm | seed 0 | seed 1 | seed 2 | mean | seed spread |
|---|---:|---:|---:|---:|---:|
| `dense` | 3.8629 | 3.8596 | 3.8600 | **3.8608** | 0.0033 |
| `moe-equal-active` | 3.7687 | 3.7656 | 3.7778 | **3.7707** | 0.0122 |
| `moe-equal-total` | 3.8595 | 3.8598 | 3.8629 | **3.8607** | 0.0034 |

**Under equal active parameters, MoE wins by 0.0901 nats** — 7.4x the widest
single-arm seed spread, so the effect is well clear of run-to-run noise. Twice
the stored parameters bought a real improvement at identical compute per token.

**Under equal total parameters, the two arms are indistinguishable**: 3.8607
against 3.8608, a gap of 0.0001 against seed spreads of 0.0033 and 0.0034. The
honest reading is not "MoE ties dense" but "this ladder cannot tell them
apart." What the MoE arm did buy is on the compute side: it reached the same
loss while passing each token through 33.2% fewer parameters.

Both statements are true simultaneously. Reporting either one alone as "MoE
beat dense" or "MoE did not beat dense" would be a defensible sentence and a
misleading result, which is the entire reason this rung runs both arms.

## Wall-clock, the budget definition this rung did not buy

| Arm | per-seed wall-clock | median tok/s | against dense |
|---|---|---:|---:|
| `dense` | 842.6s, 995.3s, 840.7s | 237,360 | 1.00x |
| `moe-equal-active` | 1646.8s, 1645.6s, 1645.9s | 121,514 | 0.51x |
| `moe-equal-total` | 1562.1s, 1560.8s, 1561.8s | 128,057 | 0.54x |

Throughput uses the median rather than the mean because dense seed 1 took 18%
longer than its two siblings while training an identical model on identical
batches — machine contention, not an architectural cost, and averaging it in
would quietly move the number.

Both MoE arms run at roughly half of dense throughput. `moe-equal-total`
performs *less* arithmetic per token than dense and still takes 1.85x as long,
which is the routing overhead measured rather than argued: a gather, a scatter,
and per-expert matmuls too small to fill the card, against a dense path sitting
on the most mature kernel in the stack.

**The consequence for the third budget definition: in the 1,645.9 seconds
`moe-equal-active` needed, the dense arm would have trained on 391M tokens
instead of 200M — 1.95x the data.** Whether it would still have lost is not
established here, because that arm was not run. Under equal wall-clock this
rung has no result, and the 0.0901 nats above are not evidence about it.

## What this run does not establish

- **Anything beyond in-distribution fit.** Every loss is measured on a held-out
  slice of the same FineWeb-Edu shards the arms trained on, so the ranking is
  by how well each predicts educational web text — not by capability. In
  perplexity the win is 47.5 down to 43.4. See the method limitations in
  [`2026-07-29-five-rungs.md`](2026-07-29-five-rungs.md), which apply here too.

- **That the equal-active win survives at a larger size.** 33M parameters over
  200M tokens is far below the scale at which mixture-of-experts is usually
  argued for. The ranking could grow, shrink, or invert.
- **Anything under an equal-wall-clock budget**, for the reason above.
- **That the routing overhead is intrinsic.** It is a property of this
  implementation on this card. A fused grouped-GEMM kernel would change the
  wall-clock column and none of the loss columns.
- **That three seeds is enough for a 0.0001 gap.** It is enough to say that gap
  is smaller than the noise; it is not enough to say the two arms are equal.
