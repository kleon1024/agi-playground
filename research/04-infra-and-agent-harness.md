# Open-Source LLM Inference/Infra & Agent Harness Landscape (Mid-2026)

> Research pass conducted 2026-07-24 with parallel web-research agents; sources linked inline.

## (a) Inference Engines — What a Curriculum Must Teach

The field has consolidated around a shared vocabulary of mechanisms, even as vLLM and SGLang trade leadership month to month. Core concepts to teach, in dependency order:

- **PagedAttention / paged KV cache**: treats GPU KV memory like OS virtual memory — non-contiguous physical blocks addressed via a logical block table, eliminating fragmentation from naive contiguous allocation. This is vLLM's foundational SOSP 2023 idea and still the base abstraction every modern engine builds on.
- **Continuous (iteration-level) batching**: scheduling happens per forward-pass, not per request — sequences enter/exit the batch every iteration rather than waiting for a full batch to finish, which is what actually drives GPU utilization gains (vLLM's "Anatomy of vLLM" blog is a strong primary source).
- **Prefill/decode disaggregation**: splitting the compute-bound prefill phase from the bandwidth-bound decode phase onto separate GPU pools. This is the dominant 2025–2026 production pattern — Meta, LinkedIn, Mistral, and HuggingFace run vLLM disaggregated; NVIDIA's Dynamo and TensorRT-LLM ship it as a first-class router/worker topology (prefill worker → smart KV-aware router → decode worker).
- **Speculative decoding**: no longer a research curiosity — EAGLE-3 (and DeepSeek's built-in Multi-Token Prediction) is now a default acceleration layer in vLLM/SGLang, giving 2–6.5x gains at low concurrency. Worth teaching the draft-model/verify loop plus why acceptance rate governs speedup.
- **Quantization**: GGUF (llama.cpp's format) vs. MLX-native quantization on Apple Silicon is a good comparative teaching unit — same Q4 model, ~5–10% memory delta, MLX ~30-40% faster prompt processing on Mac but weaker batching maturity versus llama-server's more mature scheduler.
- **mlx / llama.cpp**: valuable as the "single-GPU / consumer-hardware" counterpoint to the datacenter engines — teaches the same concepts (KV cache, batching, quantization) at a scale a student can run on their own laptop.

**Minimal teaching implementations**: **nano-vLLM** (~1,000–1,200 lines) is the single best pedagogical artifact in this space — it reimplements PagedAttention-style scheduling, prefix caching, tensor parallelism, and CUDA graphs at a scale readable in an afternoon. This should be the spine of the inference module: read nano-vLLM, then map each piece to its production analog in vLLM's actual source and the "Anatomy of vLLM" write-up.

TensorRT-LLM remains the NVIDIA-native path (in-flight batching, disaggregated serving via Dynamo's router/worker split) — useful to mention but likely out of scope for hands-on exercises given its C++/build complexity versus vLLM/SGLang's Python-first design.

## (b) Training Infra — Single-GPU-Teachable vs. Simulated Multi-GPU

**FSDP2** is now the recommended default: rewritten on PyTorch's DTensor abstraction, per-parameter (not flattened) sharding, and reportedly up to ~5x higher throughput than DeepSpeed ZeRO-3 in overlapping memory regimes, mainly via cleaner `torch.compile` integration. Practical 2026 guidance: FSDP2 for most fine-tuning on 2–8 GPUs; DeepSpeed still wins for MoE training or heavy CPU offload at >10B params.

Single-GPU-teachable fundamentals (all can be exercises without needing multi-GPU hardware): gradient accumulation (decoupling micro-batch from effective batch size), activation/gradient checkpointing (recompute vs. store trade-off, ~10% additional throughput available via selective checkpointing), and mixed precision (bf16/fp16, ~2x larger feasible batch size). The curriculum should teach these three on one GPU, then explain how they compose differently under FSDP2/ZeRO-3 sharding (gradient accumulation interacts non-trivially with sharded optimizer states).

Multi-GPU concepts that need to be *simulated or run on rented compute* (Modal is the natural fit for a solo builder): tensor/pipeline parallelism, ZeRO stage transitions, and multi-node all-reduce behavior — best taught via a small Modal job with 2–4 GPUs rather than pretending to teach it on a laptop.

**Profiling**: PyTorch Profiler for step/op-level visibility → Nsight Systems for system-wide timeline (CPU/GPU/memory transfers) → Nsight Compute for per-kernel deep-dives (occupancy, bandwidth, warp stalls). Nsight Systems 2026.1.1 added Python 3.14 sampling and richer PyTorch module annotations — worth a short profiling lab pairing a deliberately slow training step with Nsight Systems to find the bottleneck, then Nsight Compute to explain why.

## (c) Agent Harness Engineering

A "harness" is the software layer around the model that makes it an agent: the loop (observe→act→observe), tool schemas/definitions, context management (what gets loaded eagerly vs. retrieved just-in-time via glob/grep-style tools), sandboxing/permissions, and sub-agent orchestration. 2026 write-ups on Claude Code converge on: simplicity beats complex orchestration; permission and context-management design should precede model integration; sub-agents need isolated contexts and depth limits; parallel/background sub-agent execution (tens to hundreds per session) is now expected.

Reference implementations spanning the design spectrum, good as compare/contrast teaching material: **mini-swe-agent** (radically simple bash-first loop, from the SWE-bench/SWE-agent team — the best "read the whole harness in one sitting" example), **SWE-agent** (introduced the agent-computer-interface abstraction), **OpenHands** (generalist platform, much larger community), and **smolagents** (HF's minimal code-agent library). A recent notable paper, "Stop Comparing LLM Agents Without Disclosing the Harness," makes an explicit curricular point: benchmark results are meaningless without pinning down harness details — good framing for a lesson on why harness design *is* the independent variable.

Environment design for tool-use evaluation: **τ-bench / τ²-bench** (Sierra Research) model realistic multi-turn tool-agent-user interaction with policy adherence as a pass/fail criterion (not just task completion) — τ²-bench (2026) added dual-control (both user and agent can call tools), telecom domain, and full-duplex voice evaluation. Excellent template for student-built "environment + policy" exercises.

## (d) Evals

**Inspect AI** (UK AISI, with Arcadia Impact and Vector Institute) is the leading open framework for reproducible evals, and its **inspect_evals** repo now includes AgentThreatBench, operationalizing the OWASP Top 10 for Agentic Applications (2026) as executable security/utility tasks — a strong template for teaching agent-safety eval design. **lm-evaluation-harness** (EleutherAI) remains the standard for static/non-agentic benchmark running. For coding-agent evals: **SWE-bench Verified** is now widely flagged as contamination-prone; **SWE-bench Pro** is the recommended successor for real signal. **Terminal-Bench 2.0** (89 hand-verified tasks spanning sysadmin, ML, security, data science) is the emerging standard for terminal-agent evaluation. **GAIA** (466 multi-step web/file/tool tasks, human-graded, tiered difficulty) remains relevant but explicitly harness-sensitive — must control for scaffold when comparing models. A good capstone teaching point: benchmarks without disclosed harness/scaffold are not comparable (ties back to the harness section).

## (e) Serving/Experiment Infra for a Solo Builder

**Modal** is the practical default for a solo builder needing occasional multi-GPU access: Python-first serverless GPU functions, Volumes for persisting weights/checkpoints across runs (cutting cold starts from minutes to seconds), and native support for SFT/LoRA/full fine-tunes on H100/B200/A100 in a single file — good fit for the "simulate multi-GPU" exercises above. For experiment tracking, **wandb** remains the incumbent, but **Trackio** (Hugging Face, released 2025, <1,000 lines, SQLite-local + optional HF Spaces sync, drop-in `import trackio as wandb` API compatibility) is now a credible lightweight, hackable, local-first alternative — arguably better suited to a teaching repo since students can read the entire tracker's source in one sitting, mirroring the nano-vLLM philosophy.

## Curriculum takeaway

The throughline across all five areas is *pair a minimal, fully-readable implementation with the production system it mirrors* — nano-vLLM ↔ vLLM, mini-swe-agent ↔ OpenHands/Claude Code, Trackio ↔ wandb, single-GPU FSDP2 exercise ↔ Modal multi-GPU run. This "read the toy, then map to the real thing" pattern is what the strongest 2025–2026 educational resources in this space (nano-vLLM's own blog, the vLLM "Anatomy" post, mini-swe-agent) already use, and it scales well to a solo-authored teaching+practice repo.
