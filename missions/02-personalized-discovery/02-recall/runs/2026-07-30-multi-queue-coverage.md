# Run — stage 02 recall, multi-queue coverage and exact-vs-approximate search

**Date:** 2026-07-30
**Hardware:** Apple Silicon (arm64), 10 cores, macOS (Darwin 24.6.0). CPU-only;
no GPU involved anywhere in this stage.
**Cost:** \$0 (local lane). `core/recall.py` is stdlib-only; `prod/faiss_recall.py`
uses `faiss-cpu` 1.14.3 (installed in this repo's `uv` environment).

## Command and output — five queues, full catalogue

```bash
python core/recall.py --catalogue-size 400 --seed 0
```

coverage by target provenance (which queue alone can find each one):
  two_tower      20/20 found (1.00)

## Command and output — disabling each queue in turn

```bash
python core/recall.py --catalogue-size 400 --seed 0 --disable <queue>
```

| Disabled queue | Mean coverage | That queue's own target row |
|---|---|---|
| (none) | 1.00 | — |
| `two_tower` | 0.84 | 8/20 (0.40) |
| `lexical` | 0.80 | 4/20 (0.20) |
| `item_to_item` | 0.95 | 16/20 (0.80) |
| `freshness` | 0.84 | 7/20 (0.35) |

Every other queue's own row stayed at or near 20/20 in each of these four
runs — the drop concentrates almost entirely in the disabled queue's own
target category, confirming the README's claim: disabling a queue removes
close to exactly the targets only it could reach, and the rest barely move.

## Command and output — FAISS exact vs. approximate

```bash
python prod/faiss_recall.py --catalogue-size 5000
```

```
catalogue: 5000 items, 32-dim vectors (synthetic, illustrative only)

exact  (IndexFlatIP)   1.133 ms for 160 queries
approx (IndexHNSWFlat) 0.576 ms for 160 queries

approx recall@25 against the exact index: 0.913
```

```bash
python prod/faiss_recall.py --catalogue-size 5000 --ef-search 64
```

```
catalogue: 5000 items, 32-dim vectors (synthetic, illustrative only)

exact  (IndexFlatIP)   0.911 ms for 160 queries
approx (IndexHNSWFlat) 0.714 ms for 160 queries

approx recall@25 against the exact index: 0.984
```

## Verdict

Both the five-queue coverage story and the exact-vs-approximate trade-off ran
for real, on this machine, this session. Raising `--ef-search` from its
default to 64 moved recall from 0.913 to 0.984 while narrowing (but not
closing) the latency gap to the exact index (0.576 ms -> 0.714 ms vs. 1.133 ms
-> 0.911 ms) — recall bought back at a real, measured latency cost, not a
theoretical one. All numbers are from synthetic catalogues generated by the
scripts themselves; per the README's own evidence boundary, none of this
characterizes a real production catalogue.
