# Upcycling the 88M dense checkpoint into a 258M mixture of experts

## Command

```bash
cd 01-language-model/02-pretrain/upcycling/core
python upcycle.py convert ~/agi-playground/stage02/ckpt/ckpt.pt ~/moe-upcycled.pt \
    --experts 4 --active 2
python upcycle.py verify ~/moe-upcycled.pt \
    --parent ~/agi-playground/stage02/ckpt/ckpt.pt \
    --data ~/agi-playground/data/tokens --iters 20
```

## Parent

The 3.0B-token checkpoint from
[stage 02](../../): 88,197,888
parameters, 12 layers, `d_model` 768, `d_ff` 2048, 12 query heads over 4 KV
heads, 16,512-token vocabulary. Step 22,888, 2,999,975,936 tokens seen.

## Result: the surgery preserved the function

```
max |logit difference| dense vs upcycled: 1.261e-04
PASS: the upcycled model computes the parent's function

validation loss over 20 batches of 8x1024 tokens
  parent   3.0498
  upcycled 3.0499
  untrained floor would be ln(16512) = 9.7118
```

**A 258M-parameter model scored 3.0499 having done no training at all**, and its
88M parent scored 3.0498 on the identical batches. The difference is 0.0001
nats, and it is not zero for an uninteresting reason: the MoE path sums two
weighted expert outputs where the dense path sums one, so floating-point
accumulation order differs. The logit gap of 1.26e-4 is that arithmetic, not a
difference in the function.

The number to compare against is 9.7118. An error anywhere in the remap — a
transposed attention matrix, a mislabelled expert, a router that is not small,
a shared expert that adds a second copy of the feed-forward — would have shown
up as a loss somewhere between that floor and this result. Getting the parent's
loss back to four decimal places is a much stronger check than "it loads
without an exception".

### Why it comes out exact

Two initialization choices, and both are load-bearing:

- **Every routed expert is an identical copy of the dense feed-forward.** Top-k
  routing renormalises its weights to sum to one, so `w1*F(x) + w2*F(x) = F(x)`
  for any weights the router produces. The routing is therefore irrelevant to
  the output at step 0, which is exactly what makes the check possible.
- **The router is small and random, not zero.** Zero would make every expert
  equally likely forever. Random breaks the symmetry: from step 1, expert 3 has
  seen a different subset of tokens than expert 5 and receives a different
  gradient, so the four copies diverge into four different functions.

One consequence worth stating because it looks like a bug and is not: **the
router's own gradient is exactly zero at step 0.** With identical experts the
output does not depend on the routing weights, so nothing flows back to the
router matrix. It becomes non-zero the moment the experts differ, which is one
step later.

## What each initialization choice is worth

The claim above is that replication and the zeroed shared expert are what make
the surgery exact. That is only worth asserting if the alternatives were tried,
so `upcycle.py ablate` builds each one and scores it on the same 20 batches:

```
parent (dense)                               3.0498
replicate experts, zero shared               3.0499   +0.0001 vs parent
replicate experts, router zeroed             3.0498   +0.0000 vs parent
copy shared expert instead of zeroing        3.7949   +0.7451 vs parent
first expert copied, rest random            10.5968   +7.5469 vs parent
all experts random                          13.0573   +10.0075 vs parent
untrained floor, ln(vocab)                   9.7118
```

Four things this table settles:

- **The router's value genuinely does not matter at step 0.** Zeroing it
  reproduces the parent to four decimals, which is the arithmetic argument made
  concrete. It is still the wrong initialization, because a zero router leaves
  every expert equally likely forever and the copies never diverge.
- **The zeroed shared expert is load-bearing, and costs 0.745 nats when
  skipped.** A copied shared expert runs on every token *in addition to* the
  routed ones, so the block emits roughly twice the feed-forward contribution
  the residual stream was trained to receive.
- **Partial copying is not a partial result.** With one expert copied and three
  random, top-2 of 4 puts a random expert in the mix for almost every token and
  the model lands at 10.60 — above the untrained floor.
- **All-random experts score 13.06, worse than knowing nothing by 3.35 nats.**
  This is the most useful row. An untrained model spreads probability roughly
  evenly and is merely uninformative; this one has trained embeddings and
  trained attention driving random feed-forwards, so it commits confidently to
  wrong tokens, and cross-entropy punishes a confident error far harder than
  uncertainty. "Worse than the floor" is a signature of trained weights wired
  wrongly, and it is worth recognising because it is what a botched remap
  actually looks like.

Every one of these variants loaded without an exception and printed a
plausible-looking number. That is the argument for making the acceptance test a
loss comparison against the parent rather than a successful `load_state_dict`.

## Continuing to train it: the first thing that goes wrong

A 4e6-token smoke test of `continue_training.py --arm moe` at `lr=1e-4`,
micro-batch 8, accumulation 2:

```
moe: starting val loss 3.0847
  step    50  tokens     0.8M  val 3.1178    16.5k tok/s
  step   100  tokens     1.6M  val 3.1166    16.5k tok/s
  step   150  tokens     2.5M  val 3.1119    16.6k tok/s
  step   200  tokens     3.3M  val 3.1072    16.6k tok/s
  step   244  tokens     4.0M  val 3.1044    16.6k tok/s
```

Two measurements, both of which change how the real comparison has to be run.

**Loss went up before it came down.** The parent finished a cosine schedule at
nearly zero learning rate, sitting in a minimum; raising the rate to 1e-4 kicks
it back out. It is recovering by the end of the window and has not yet returned
to where it started. Any continued-training comparison shorter than that
recovery measures the disruption rather than the architecture, which is why the
comparison run is budgeted at 2e8 tokens.

**16.6k tokens per second** over this 4M-token window. The cause of the
slowdown is the Python loop over experts in
`01-language-model/02-pretrain/architecture-ablations/core/model.py`, not the
architecture. It is reported here because it decides what fits in a session,
and because a wall-clock-equal comparison would be a comparison of kernel
maturity rather than of model shape.

> **Superseded.** This figure is dominated by startup across only 244 steps,
> and an earlier version of this record compared it against a
> differently-configured pretraining run to claim "roughly ten times slower".
> Sustained over 200M tokens the upcycled model reaches 55,069 tok/s against
> the dense arm's 106,369 measured in the same script on the same data — 1.93x,
> not 10x. See
> [`2026-07-28-continue-training.md`](2026-07-28-continue-training.md).

Note that the 3.0847 starting figure comes from this script's evaluation
protocol — 8 batches, seed 999 — and not the 20-batch, seed-0 protocol that
produced 3.0499 above. They are different samples of the same held-out file and
should each be compared only within their own table.

## What this run does not establish

- **That the upcycled model is better.** It establishes that it is *the same*,
  which is the precondition for asking whether it gets better. The comparison
  that matters is against continuing to train the parent for the same budget,
  because that is what the same GPU-hours would otherwise buy. That run is
  `core/continue_training.py` and it has not been recorded here yet.
- **That 4 experts at top-2 is a good shape.** It was chosen because it makes
  the identity check clean, not because it was tuned. Wider or narrower
  experts, more or fewer, and a shared expert are all untested.
- **Anything about wall-clock.** The expert dispatch in
  `01-language-model/02-pretrain/architecture-ablations/core/model.py` is a Python loop
  over experts. A probe at 33M parameters measured roughly half the tokens per
  second of the dense arm at equal FLOPs, which is kernel immaturity rather
  than a property of the architecture — the same distinction
  [the serving chapter](../../../05-serve/why-concurrency-pays/)
  had to make between a scheduling policy and a fused kernel.
- **That this generalises to a changed embedding space.** It does not, and that
  is the point of the precondition. Everything here works because the tokenizer
  and `d_model` are unchanged, so every copied tensor still means what it meant.

## Notes

- The parent's validation loss is quoted in
  [its own run record](../../runs/2026-07-28-pretrain-3b.md)
  as 3.0984 at the final step, measured by the training loop over its own
  evaluation sample. The 3.0498 here is a different sample of the same held-out
  file — 20 batches of 8x1024 with a fixed seed — so it should be compared with
  the 3.0499 beside it and not with the training loop's figure.
- `head.weight` is absent from the saved state dict by design: it is tied to
  `tok.weight`, and `convert` asserts that it is the *only* missing tensor
  rather than loading with `strict=False` and hoping.
