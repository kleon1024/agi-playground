# Run — the token tax by input class, measured on the frozen tokenizer

**Date:** 2026-08-08
**Command:** `uv run python core/token_tax.py`
**Hardware:** Apple M1 Pro, macOS 15.6.1, CPU-only.
**Software:** Python 3.12.9 via uv; stdlib only, plus the stage's own
`core/bpe.py` tokenizer module.
**Wall-clock:** 0.06s.
**Cost:** \$0 (local lane).

## Purpose

The stage's tokenizer reports one aggregate number, chars per token, and
every product decision that consumes tokens — context budget, pricing,
throughput — treats a token as equal. This run reads the tax per class
on the real frozen tokenizer (`tokenizer.json`, 16,384 ids, byte-level
BPE): a panel of realistic inputs is tokenized and converted into pieces
per character and the context-budget consequence (how many characters of
each class fit in a 4,096-token window). The second half is the
case-finding step: a realistic mixed document is segmented into class
runs, each run is tokenized separately, and the run prints the ledger —
share of characters versus share of tokens per class.

## Reading the output

- **The tax varies by two orders of magnitude.** English prose costs 0.24
  tokens per character (about 4.2 chars per token), CJK 2.96 (a 27-char
  sentence is 80 tokens), and emoji 4.00 (each emoji is 4 bytes, so 4
  tokens). Accented Latin, dates, and phone numbers sit between — each
  carries a real per-class cost.
- **The context budget is not fair.** A 4,096-token window holds 17,246
  characters of English but 1,382 of CJK and 1,024 of emoji — an order of
  magnitude less non-Latin text. A product that caps context at N tokens
  silently gives CJK users an N/12 effective window.
- **The ledger is the case-finding step.** In the mixed document, CJK is
  4.3% of the characters but 23.5% of the tokens, emoji 1.1% of the
  characters but 7.8% of the tokens; digit, CJK, and emoji runs together
  are 17% of the characters and 47% of the tokens. The chars/token
  aggregate cannot see any of this — only the per-class ledger can.
- **The number edge is the same mechanism at small scale.** The big
  integer `1234567890` costs 6 tokens (`12|3|45|6|78|90`) because the
  pre-tokenizer caps digit runs at 3, which is the tokenization-side
  mechanism behind the arithmetic failures cited in the tie-break chapter
  (Singh et al., arXiv:2402.14903, Feb 2024).
- **Deterministic and reproducible.** Same frozen tokenizer, same panel,
  same numbers on every run.

## Evidence boundary

This run measures the real frozen tokenizer on a hand-picked panel — the
per-class rates are exact for this tokenizer and these inputs, and the
ledger is exact for this document. The panel is not a corpus: real
mixed-language workloads have their own class distributions, so the
product consequence (how much a fixed budget shrinks for CJK users) is a
measured rate on representative inputs, not a claim about every workload.
The arithmetic consequence of number fragmentation is cited, not
re-measured here: Singh et al. (arXiv:2402.14903, Feb 2024) show number
tokenization style changes arithmetic behavior on frontier models, with
left-to-right digit runs producing stereotyped errors concentrated on
digit 4. No model was trained here.
